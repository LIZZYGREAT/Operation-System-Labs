## 一、先建立问题：一份内核代码如何获得 CPU 的控制权？

### 1. 普通 C 程序为什么可以从 `main` 开始理解

假设写下：

```c
#include <stdio.h>
int main(void) {
    printf("hello\n");
    return 0;
}
```

在已经运行 Linux 的计算机上，我们输入 `./a.out`，操作系统会帮我们做很多事：读取 ELF 文件、创建进程、映射程序的代码和数据、准备用户栈、设置初始寄存器和程序计数器，把执行机会交给程序。甚至在进入 `main` **之前**，还会执行运行时入口代码（例如 C 运行时的启动过程）。

因此我们习惯的“程序从 main 开始”是一种**已经有人做好准备之后**的视角，而不是 CPU 的自然规律。

现在换个题目：**我们写的程序就是操作系统内核本身。** 它不能要求一个已经存在的 Linux 先替它创建进程、分配用户栈、调用 `main`，否则就陷入“谁来启动第一个操作系统”的循环。

我们必须自己回答三件事：

1. **代码在哪里？** 一串机器指令必须先放在 CPU 能访问的内存位置。
2. **CPU 从哪里开始读？** CPU 必须有一个确定的初始程序计数器（PC），才能读到第一条指令。
3. **代码能够安全运行吗？** 后续 C 函数可能使用栈、全局数据、设备接口，这些条件必须逐步建立。

这就是本次实验的起点。后面出现的每个组件，基本都在回答上面某个问题。

### 2. 不要把三个不同过程混为一谈

```text
构建阶段（开发机上）              运行阶段（虚拟 RISC-V 机器中）
C / 汇编源码                       QEMU 创建机器并放置固件、内核镜像
   ↓                                ↓
交叉编译、链接                    Reset ROM：执行第一条指令
   ↓                                ↓
ELF / 裸镜像                      OpenSBI：准备并交接给内核
                                    ↓
                                 kern_entry：准备内核自身环境
                                    ↓
                                 kern_init：执行 C 代码
```

**关键区别**：**“把代码放进内存”与“让 CPU 跳过去执行”是两件事。** 实验里的 QEMU loader 可以在 CPU 执行前把内核放到 `0x80200000`，但这不等于复位 PC 自动变成 `0x80200000`。

## 二、CPU 是怎么工作的：为什么要先学 PC、寄存器和指令

### 1. 最简 CPU 执行模型

先想象内存是一个按地址排列的字节数组：

```text
地址             内容
0x1000           某条机器指令的字节
0x1004           下一条机器指令的字节
...
```

CPU 有一组寄存器，用来临时保存数值、地址和状态。其中 **PC（Program Counter，程序计数器）** 表示接下来要从哪个地址取指。一个简化循环是：

```text
读取 PC 指向的指令
→ 译码
→ 执行（修改寄存器/内存）
→ 确定下一条指令的 PC
→ 重复
```

大部分普通顺序指令执行后，PC 前进到下一条；跳转、分支、异常返回等指令则可能直接改写控制流。RISC-V 还有 16 位压缩指令（RVC），所以**指令地址不总是每次加 4**；本实验的 `0x80200008 → 0x8020000a` 就只相差 2 字节。

**CPU 不认识 C 函数名。** `kern_entry`、`kern_init` 是汇编器/链接器/调试器识别的符号；CPU 真正执行的是某个地址上的机器指令。

### 2. 为什么需要寄存器

假设有一条指令要把两个数相加。CPU 可以把这两个数先放到寄存器里，再由 ALU 计算。RISC-V 64 位整数寄存器宽 64 位，常见名字如下：

| 寄存器 | 角色 | 本实验怎么用 |
|---|---|---|
| `pc` | 下一条要执行的指令地址 | 观察 `0x1000 → 0x80000000 → 0x80200000` |
| `sp`（`x2`） | 栈指针 | `kern_entry` 将其设置为内核栈顶 |
| `t0`（`x5`） | 临时寄存器 | Reset ROM 用它保存跳转目标 |
| `a0`（`x10`） | 参数/返回值寄存器 | 启动时传 hart ID；SBI 调用时存参数/返回值 |
| `a1`（`x11`） | 参数寄存器 | 启动时传设备树地址 |
| `a7`（`x17`） | 按调用约定有特定用途 | 本实验旧版 SBI 中保存调用编号 |
| `ra`（`x1`） | 返回地址 | 普通函数调用可以用它记录返回位置 |

这里的 `a0`、`t0` 是**寄存器的约定用途**，不是芯片里两种不同的寄存器。对某一次调用，“哪个值放哪个寄存器”由 ABI（应用二进制接口）和具体调用约定决定。

### 3. 指令、伪指令与汇编：别把源码文本和 CPU 指令混为一谈

汇编代码：

```asm
la sp, bootstacktop
```

人容易读懂，但 `la` 是一种**伪指令**：汇编器将其翻译为真实机器指令序列。原因是目标地址可能有 64 位，单条固定长度的普通指令放不下完整地址。

本实验反汇编实际显示：

```asm
0x80200000: auipc sp,0x3
0x80200004: mv    sp,sp
0x80200008: j     0x8020000a <kern_init>
```

其中 `mv` 和 `j` 也是反汇编器可能采用的伪指令表示形式。**GDB 的 `si` 是执行一条实际机器指令，不是执行一行源码。**

## 三、现在终于能够回答：为什么 CPU 必须有 Reset 和 Reset Vector

### 1. 复位是在解决什么问题

CPU 正在运行时，寄存器可能存着任意之前的值，PC 可能指向任意程序代码。如果我们按“重启”，总不能让它继续从一个未知地址执行。

因此硬件/虚拟机器定义 **Reset（复位）机制**：让 CPU 进入约定的初始状态，并为开始取指提供确定入口。这个入口称为 **Reset Vector（复位向量）**。

Reset Vector 不是“存放所有操作系统代码的地址”，它只需能保证：**CPU 复位后有第一步可走，随后通过启动代码继续找到下一阶段。**

### 2. 为什么需要最小启动 ROM

复位时，内存里未必已经有完整操作系统，而且不同板卡的外设、启动介质可能不同。所以机器往往会让 CPU 先执行一小段已知的启动代码，完成最基础的跳转或准备工作。

**ROM（Read-Only Memory）** 原意是只读存储器。在 QEMU 这样的虚拟机器里，“Reset ROM”主要描述一种面向 CPU 的启动只读代码区域/语义；它不是说我们一定有一块真实焊在主板上的 ROM 芯片。

本实验的 QEMU `virt` 机器，GDB **实际测到初始 PC 为 `0x1000`**。这属于当前机器模型和 QEMU 版本的启动布局，不能推广为“所有 RISC-V CPU 永远从 `0x1000` 启动”。

### 3. 五条真实的 Reset ROM 指令，逐条解释

本实验日志为：

```asm
0x1000: auipc t0,0x0
0x1004: addi  a1,t0,32
0x1008: csrr  a0,mhartid
0x100c: ld    t0,24(t0)
0x1010: jr    t0
```

不要先急着背。下面把每条指令都翻译为“执行前需要什么、执行后改变什么”。

#### （1.）`auipc t0,0x0`：先获得自己的位置

`auipc` 全称 **Add Upper Immediate to PC**。它使用**该指令自身的 PC** 以及一个立即数，计算：


$$\mathrm{rd} = \mathrm{PC}_{\text{当前指令}} + \operatorname{sext}(\mathrm{imm20}\ll12)$$

- `rd` 是要写入的目标寄存器。
- `imm20` 是指令中的 20 位立即数字段。
- `<< 12` 表示左移 12 位，相当于乘以 \(2^{12}=4096\)。
- `sext` 表示按架构规则做符号扩展。

在 `0x1000` 执行 `auipc t0,0x0`：

$$ t0=0x1000+(0\ll12)=0x1000 $$

**为什么要这样绕一圈？** 因为随后的启动代码需要通过“相对当前位置的偏移”定位它附近保存的数据，而不是把某个长地址硬编码在这条指令里。这属于 **PC-relative addressing（PC 相对寻址）**。

#### （2.）`addi a1,t0,32`：计算一个地址

`addi` = Add Immediate：

$$a1=t0+32=0x1000+0x20=0x1020$$

注意这里的 `32` 在汇编里是十进制，等于 `0x20`。`a1` 得到一个**地址**，不是立刻把该地址处的内容读出来。本实验的启动约定使用它传递设备树（FDT）的指针。

#### （3.）`csrr a0,mhartid`：读一个特殊硬件状态寄存器

`csrr` 可以理解为“从 CSR 读取值”。**CSR（Control and Status Register）** 不是普通内存变量，而是 CPU 用于暴露控制/状态信息的一类专用寄存器。

`mhartid` 保存当前硬件线程的 ID。执行后：

```text
a0 = 当前 hart ID
```

这里 **hart = hardware thread**，可以先理解成“能够独立取指和执行指令的一条硬件执行流”。多核或多硬件线程处理器可有多个 hart，启动代码需要知道目前是哪一个。

#### （4.）`ld t0,24(t0)`：从内存读取真正的跳转目标

`ld` = Load Doubleword。在 RV64 语境里，它读取 **8 字节**。

```asm
ld t0,24(t0)
```

表示以旧 `t0` 为基址，偏移 24 字节，读出该地址中保存的 64 位值，写回 `t0`：

$$t0 \leftarrow \mathrm{Mem64}[0x1000+24]
=\mathrm{Mem64}[0x1018]$$

实际调试中，随后跳去了 `0x80000000`，说明该次执行取出的目标地址是 `0x80000000`。

区别：`addi` 是**计算一个地址/数值**；`ld` 才是**访问该地址处的内存内容**。

#### （5.）`jr t0`：把控制权交给下一阶段

`jr` 可以理解成 Jump Register：跳到寄存器 `t0` 给出的地址；在 RISC-V 中是对相应 `jalr` 行为的汇编别名。

本次执行：

```text
跳转前：t0 = 0x80000000
执行 jr t0
跳转后：PC = 0x80000000
```

由此完成：

```text
Reset ROM 只做必要的起始准备
          ↓
将 hart ID / 设备树地址留在参数寄存器
          ↓
跳转到固件入口
```

**至此，我们没有“启动内核”。我们仅仅找到了比 Reset ROM 更强的下一阶段启动程序。**

## 四、Firmware、Bootloader、OpenSBI：为什么下一站不是内核

### 1. 固件在解决“谁来处理硬件早期事务”的问题

操作系统最终要管理处理器、内存和设备，但它尚未启动时，不能假定已经有人替它完成全部机器级准备。某些操作也不应让后续 S-mode 内核随意直接执行。

**Firmware（固件）** 是处在硬件与更高层软件之间的低层软件。它可能负责早期平台初始化、启动阶段切换、保留必要的底层运行服务。固件不是一个特定的文件格式，也不等同于某个唯一产品。

**Bootloader（引导加载器）** 按职责命名：主要负责找到/加载一个可启动程序并交出控制权。固件和引导加载器的功能可能有交叠，但不能简单把两个词当同义词。

本实验必须分清：

- **QEMU loader**：根据命令行，在运行前把 `ucore.img` 的字节加载到指定内存地址。
- **Reset ROM**：CPU 最开始执行的少量启动指令，跳到下一阶段。
- **OpenSBI**：此实验使用的低层固件，负责机器级服务和交接给内核。
- **`kern_entry`**：我们自己内核接到控制权之后的第一段指令。

因此 **“加载内核字节”不是 OpenSBI 在这份配置中的必要工作**；QEMU 的 loader 已经完成这项工作。OpenSBI 负责的是启动和特权层面的衔接。也不能把 OpenSBI 解释成“只负责跳转的一段代码”，因为内核运行后它还会响应 SBI 请求。

### 2. 为什么一个阶段不能包办全部

想象复位后直接进 C 内核：

- 内核需要先知道自己从哪个地址开始执行。
- C 函数通常需要有效的栈。
- 内核需要了解当前机器，并可能使用机器级服务。
- 某些机器操作被特权架构限制在 M-mode。

可以把它们全部硬塞进某个巨大入口，但这样会将**机器相关启动细节、机器服务与操作系统逻辑强耦合**。分层的价值是：把平台最底层的启动/机器服务放到固件，操作系统通过约定接口使用服务；内核自身则负责自己的栈和后续 OS 初始化。

这不是硬件强制规定“必须有 OpenSBI”，而是本实验采用的 RISC-V 软件栈设计。

## 五、为什么 RISC-V 要有特权级（M/S/U）

### 1. 从“所有代码都能做任何事”的危险开始

假设任意应用代码都可以直接改变全局中断设置、关闭整个机器或随意访问其他程序的内存，那么任何一个普通程序错误都会破坏整机。

现代 CPU 因此提供**特权级**：不同软件能够执行的控制操作不同。RISC-V 常见层次如下：

```text
M-mode  Machine Mode
  最底层机器控制权限；本实验 OpenSBI 主要在此层

S-mode  Supervisor Mode
  操作系统内核常在此运行

U-mode  User Mode
  普通应用程序常在此运行
```

重要：**“内核”不意味着“永远拥有最高硬件权限”**。S-mode 内核已经能管理大量操作系统资源，但某些 M-mode 机器功能需要通过固件提供的服务完成。

### 2. 特权级不仅是一个标签，还限制指令的可执行性

例如本实验的 Reset ROM 读取 `mhartid`：它是机器级 CSR。能不能直接读它，与当前执行特权级有关。把特权级理解为 CPU 强制执行的访问控制，而不是软件自己约定的用户角色。

### 3. 陷入（Trap）到底是什么

当 CPU 遇到某些事件，正常顺序执行会被打断，转到预先配置的处理入口。这类控制流转移统称 **Trap**。

来源可能包括：

- **Exception（同步异常）**：与当前正在执行的指令有关，例如非法指令、`ecall`。
- **Interrupt（中断）**：通常来自定时器或外设等异步事件。

触发 trap 时，CPU 依据特权配置保存必要状态、切换到相应处理流程；处理完成后可以通过适当的异常返回指令恢复执行。

**`ecall` 不等于直接调用一个固件函数的地址。** 它请求 CPU 进入约定的异常/服务处理路径，这就是为什么 SBI 可以形成受控的权限边界。

## 六、SBI、OpenSBI 与 `ecall`：这一层真正是怎么协作的

### 1. 先分清接口、实现、调用机制

这三个概念经常被混写：

| 词 | 它回答什么问题 | 本实验的答案 |
|---|---|---|
| **SBI**（Supervisor Binary Interface） | S-mode 软件与更低层固件之间如何约定“请求什么服务、参数放哪里、结果如何返回”？ | 规定服务编号、寄存器传参和语义 |
| **OpenSBI** | 谁具体实现这个接口？ | 当前运行的固件；串口输出由它处理 |
| **`ecall`** | CPU 怎样从当前执行流进入服务处理路径？ | 执行环境调用指令，引发同步 trap |

类比软件开发中的接口与实现：知道 `print_char(c)` 的规范，并不意味着知道某个设备驱动内部如何发送字节。**接口是协议，实现是代码，`ecall` 是触发协议执行的硬件机制。**

### 2. 为什么叫 *Binary* Interface

因为在 CPU 已经执行机器指令的阶段，双方不靠 C 函数名交换请求，而靠**二进制级调用约定**：指定寄存器代表请求编号和参数，`ecall` 触发执行，返回结果也遵循寄存器约定。即使内核和固件不是由相同源码或编译器构建，也能互操作。

### 3. 跟踪当前代码中一字符的输出

`kern/init/init.c`：

```c
cprintf("%s\n\n", message);
```

格式化层最后会逐字符输出：

```text
cprintf
→ vcprintf
→ vprintfmt（解析 %s）
→ cputch（写一个字符）
→ cons_putc
→ sbi_console_putchar
→ sbi_call
→ ecall
→ OpenSBI 处理 console 服务
→ QEMU 所模拟的串口/控制台
→ WSL 终端出现字符
```

实际 `code/libs/sbi.c`（节选）：

```c
uint64_t SBI_CONSOLE_PUTCHAR = 1;

void sbi_console_putchar(unsigned char ch) {
    sbi_call(SBI_CONSOLE_PUTCHAR, ch, 0, 0);
}
```

这份代码使用的是**早期 Legacy SBI 约定**；当前输出报告的固件为 OpenSBI v0.4。对应 `sbi_call` 中：

```asm
mv x17, %[sbi_type]  # a7 = 服务编号
mv x10, %[arg0]      # a0 = 第一个参数：字符
mv x11, %[arg1]      # a1 = 第二参数
mv x12, %[arg2]      # a2 = 第三参数
ecall                  # 请求进入固件服务处理
mv %[ret_val], x10   # 从 a0 提取返回值
```

逐层解释：

- `mv` = 将源操作数的值复制到目标寄存器。`x17` 就是 ABI 名称 `a7`，`x10` 就是 `a0`。
- `sbi_type = 1` 代表此版本的控制台字符输出服务。
- `arg0 = ch` 是要发送的字符编码。
- `ecall` 执行之后，由 CPU 的 trap 处理机制进入已配置的处理路径；具体处理如何定位、切到哪个特权级，取决于当前特权设置。
- OpenSBI 的实现根据服务编号处理请求并返回；后续 S-mode 代码继续运行。

**注意版本边界**：现代 SBI 规范已引入新的扩展与调用约定，不能把此处的旧版控制台服务编号 `1` 当作所有 RISC-V 平台永久通用的打印 API。

### 4. SBI 和系统调用有什么不同

它们相似之处都是跨越一个约定的执行/权限边界，但**服务对象与边界不同**：

```text
普通 Linux syscall：
U-mode 应用 → S-mode Linux 内核

本实验 SBI 调用：
S-mode ucore → M-mode 固件服务
```

因此不能说 SBI 就是“给普通应用使用的系统调用”。

### 5. OpenSBI 把控制权给内核之后就消失了吗

不会。它不再是 CPU 当前正常执行的内核主流程，但固件仍可作为机器级服务的处理者存在。内核执行 `ecall` 时，可以再次进入由固件处理的服务路径，执行后返回内核。

## 七、为什么 OpenSBI 跳到内核之后还需要 `kern_entry`

### 1. 固件已经能执行了，为什么 C 内核不能直接开始？

这其实是**责任归属**问题：OpenSBI 已经能使用它自己的运行栈、寄存器安排，并不代表这些资源属于我们的内核，或能长期被我们安全使用。

C 编译器编译一个函数时，会默认调用者/被调用者遵守某套 **ABI（Application Binary Interface）**：哪些寄存器用于传参，哪个保存返回地址，栈怎么对齐，必要时如何保存寄存器等。

如果在内核入口还没有建立自己的栈，却贸然执行可能压栈的 C 代码，就无法确保函数的栈内操作有效。当前设计用极小的汇编入口先做**最小、明确、可预测**的初始化。

### 2. 栈不是一个特殊硬件芯片，而是一段按约定使用的内存

栈（stack）本质上是一块普通内存。CPU/编译器按照“先进后出”的规则，用 `sp` 指示当前栈顶附近的位置。RISC-V 常用 ABI 中栈向**低地址**增长。

例子：最初 `sp = 0x80203000`，某函数需要 16 字节栈帧：

```asm
addi sp, sp, -16
```

执行后：
```
sp=0x80203000-0x10=0x80202ff0
```

函数可能把寄存器值或局部数据写入这块地址，返回前再把 `sp` 恢复。**关键并不是 `sp` 本身会自动存任何东西，而是编译器生成的访存指令以 `sp` 为基址管理栈空间。**

### 3. 这块栈从哪里来

当前 `entry.S`：

```asm
.section .data
.align PGSHIFT
.global bootstack
bootstack:
    .space KSTACKSIZE
.global bootstacktop
bootstacktop:
```

- `.section .data`：告诉汇编器后面的内容安排到数据段。
- `.align PGSHIFT`：此 GNU assembler 语境中按 ($2^{PGSHIFT}$) 字节边界对齐；这里 `PGSHIFT=12`，即 4096 字节。
- `.space KSTACKSIZE`：在该段中预留指定字节数。注意这不是运行中调用 `malloc()`。
- `bootstack`、`bootstacktop`：两个表示地址的**符号标签**，它们不自动代表两个独立变量。

`mmu.h`、`memlayout.h` 定义：

$$PGSIZE=4096,\quad KSTACKPAGE=2,\quad KSTACKSIZE=8192\ \text{bytes}$$

本实验 `nm` 实测：

```text
bootstack    = 0x80201000
bootstacktop = 0x80203000
```

正好相差 `0x2000 = 8192` 字节。因栈向低地址增长，初始化应让 `sp` 指向高地址边界 `bootstacktop`。

### 4. 再回看 `la sp, bootstacktop`

`la` 的语义是“将符号的**地址**装进寄存器”，不是把 `bootstacktop` 地址处的内存读出来。本次反汇编：

```asm
0x80200000: auipc sp,0x3
0x80200004: mv    sp,sp
```

由于当前 `auipc` 指令地址为 `0x80200000`：

$$sp=0x80200000+(3\ll12)=0x80203000$$

低位补偿量恰好为 0，后续 `mv sp,sp` 不再改变值。这不是 `la` 的一般固定展开规则，而是**当前符号距离与最终链接结果**带来的效果。

### 5. `tail kern_init` 与普通函数调用的区别

常见调用指令会保存返回地址，以便未来返回调用者；尾跳转则不打算返回到当前入口。`kern_entry` 完成初始化后没有继续工作的需要，所以采用：

```asm
tail kern_init
```

本实验反汇编为：

```asm
0x80200008: j 0x8020000a
```

即直接修改 PC 跳入 `kern_init`。这里还有一个易忽略事实：`j` 被压缩编码为 2 字节，因此 `kern_init` 地址是 `0x8020000a`，而不是简单推成 `0x8020000c`。

## 八、为什么要编译、链接、放到 `0x80200000`：从“代码在哪”回到文件格式

### 1. `.c` 不等于 CPU 可以执行的东西

C 编译器把每个源文件变成目标文件（`.o`）。这些目标文件包含代码和数据，但各文件之间的函数地址与最终布局尚待确定。例如 `entry.S` 里要跳到 `kern_init`，但 `kern_init` 来自另一个文件。**链接器（linker）** 的任务是合并目标文件、解析符号引用、安排地址，并产生一个完整的可执行映像。

### 2. ELF、Section、Symbol 分别解决什么问题

- **ELF**：可执行/目标文件的一种结构化格式，含文件头、描述装载的 Program Header、节信息及可能存在的符号与调试信息。
- **Section（节）**：按用途组织的代码和数据，如 `.text`（机器指令）、`.rodata`（只读常量）、`.data`（初始化可写数据）、`.bss`（通常用于不需要在文件中逐字节保存的零初始化/未初始化数据）。
- **Symbol（符号）**：将名字与地址等信息建立联系，如 `kern_entry`、`bootstacktop`。

一个关键区分：**Section 是链接组织视角，Program Header 描述执行映像的装载视角**。二者相关但不是同一个东西。

### 3. 为什么必须有 `kernel.ld`

通用 Linux 程序通常由系统工具链默认选择合适的链接布局；我们的裸机内核却需要明确指定地址。因此 `code/tools/kernel.ld` 包含：

```ld
OUTPUT_ARCH(riscv)
ENTRY(kern_entry)
BASE_ADDRESS = 0x80200000;
SECTIONS {
  . = BASE_ADDRESS;
  ...
}
```

`ENTRY(kern_entry)` 指定 ELF 程序入口；`. = BASE_ADDRESS` 让后续节从指定地址开始排布。在本实验最终结果中：

```text
ELF entry = 0x80200000
kern_entry = 0x80200000
```

而 Makefile 的 QEMU 命令又指定：

```text
-device loader,file=bin/ucore.img,addr=0x80200000
```

二者分别是**链接时认为代码应该位于哪里**和**运行前实际把字节放到哪里**。本实验需要二者一致；但从概念上，它们不是同一种动作。

### 4. `bin/kernel` 和 `bin/ucore.img` 为什么要分两个文件

`bin/kernel` 是带入口地址、符号和调试信息的 ELF，供 `readelf`、`nm`、`objdump`、GDB 等工具解析；Makefile 又使用 `objcopy -O binary` 生成不带 ELF 文件头、符号表等元数据的裸二进制 `bin/ucore.img`，交给 QEMU loader 装入内存。

```text
.c / .S → .o → ld + kernel.ld → bin/kernel（ELF）
                               ↓ objcopy
                         bin/ucore.img（裸镜像）
```

所以 **QEMU 装入哪个文件，GDB 使用哪个文件解释符号，是两个不同问题**。当前 GDB 加载 `bin/kernel`，但实际 CPU 在模拟内存里执行的是从 `ucore.img` 得到的机器指令。

### 5. BSS 清零为什么也属于启动工作

C 语言中某些静态存储期对象应在程序开始时具有零初值。在普通进程中，操作系统装载器会保证这些区域正确初始化；裸机启动则要看具体装载方法和内核初始化代码如何保证。

当前 `kern_init` 调用：

```c
extern char edata[], end[];
memset(edata, 0, end - edata);
```

`edata`、`end` 是链接脚本提供的边界符号，并非 C 里按通常方式定义的数组。此调用意图是清理对应未初始化数据区。本实验的 `nm` 输出却显示：

```text
edata = 0x80203008
end   = 0x80203008
```

因此这次实际清零字节数为 **0**。不能仅因为看到 `memset` 就说“实际清零了 8KB 栈”；栈在 `.data` 中预留，和这里的 BSS 区间是不同概念。

## 九、GDB 在这次实验里究竟扮演什么角色

### 1. 为什么不能单靠程序输出证明所有步骤

终端出现启动消息，确实表明程序已经运行到打印逻辑；但**不能直接告诉我们 CPU 最初 PC 是多少、何时进入 OpenSBI、`sp` 如何变化**。

因此需要 GDB 观察运行状态。GDB 不是本次架构的一个启动层；它是一个**从外部观察/控制虚拟 CPU 的调试工具**。

### 2. GDB 如何调试另一个架构的 CPU

QEMU 有 **GDB stub（远程调试接口）**。GDB 通过 TCP 连接到 QEMU，向其请求读取寄存器、读取内存、暂停、单步、设断点。QEMU 负责在其模拟的 RISC-V CPU 上落实这些操作。

```text
riscv64-unknown-elf-gdb
          ↕ GDB Remote Protocol / localhost:1234
QEMU GDB Stub
          ↕
虚拟 RISC-V CPU / 内存
```

GDB 又加载 `bin/kernel` 的符号信息，因此能将机器地址 `0x8020000a` 显示为 `kern_init` 和对应源码行。

### 3. `-s` 与 `-S` 为什么必须区别理解

```text
-s ：开启默认的 TCP 1234 GDB server
-S ：启动后先让虚拟 CPU 暂停
```

只有 `-s` 而没有 `-S`，等调试器连上时 CPU 可能早已执行完启动代码；只有 `-S` 而没有调试连接手段，CPU 就停在初始位置。因此 `make debug` 使用二者组合。

### 4. 用真实 GDB 数据构成证据链

本实验成功复跑的日志：

| 观测时刻 | 值 | 说明 |
|---|---|---|
| GDB 初次连接 | `pc=0x1000` | CPU 停在 Reset ROM |
| 5 条 Reset ROM 指令后 | `pc=0x80000000` | 已跳入 OpenSBI |
| 命中内核入口断点 | `pc=0x80200000` | OpenSBI 最终交接给 kernel |
| 设置栈之前 | `sp=0x8001bd80` | 当前仍是固件使用的栈位置 |
| 执行 `auipc sp,0x3` 后 | `sp=0x80203000` | 等于 `bootstacktop` |
| 命中 C 入口 | `pc=0x8020000a` | 已进入 `kern_init` |

`pc=0x80000000` 并不意味着我们逐条理解了 OpenSBI 所有机器指令；`break kern_entry` 之后的 `continue` 也不是“GDB 代替 OpenSBI 完成了交接”，而是**让 CPU 自己继续运行，在到达内核时暂停给我们看**。

### 5. 学会真正解释每条 GDB 指令

```gdb
p/x $pc
```

打印当前 PC，`/x` 是以十六进制格式显示。

```gdb
x/5i $pc
```

`x` = examine memory；`5` = 五个单元；`i` = 以指令反汇编方式解读；`$pc` = 起始地址。

```gdb
si
```

单步执行**一条机器指令**；重复 5 次在当前 QEMU 中恰好从 `0x1000` 走到 `0x80000000`。

```gdb
break *0x80200000
continue
```

在地址 `0x80200000` 设断点，然后让虚拟 CPU 自己执行直到命中。这不是把 PC 直接修改到目标地址。

```gdb
p/x $sp
p/x &bootstacktop
```

分别读取当前栈指针和内核栈顶符号地址，验证是否相等。

## 十、把所有组件真正连成一条完整因果链

### 1. 构建链：从源码到机器内存

```text
手里只有 C / 汇编源文件
  ↓ CPU 不认识 C，所以交叉编译为 RISC-V 目标文件
多个目标文件互相引用但地址未定
  ↓ linker + kernel.ld 解析符号、决定布局
得到带符号/调试信息的 ELF
  ↓ objcopy 生成适合本次 loader 使用的裸镜像
QEMU 将镜像字节放到约定的 0x80200000
```

### 2. 执行链：从复位到 C 内核

```text
CPU 复位时不能凭空执行 C main
  ↓ 平台 Reset Vector 给出第一条指令地址
PC = 0x1000，执行 Reset ROM
  ↓ 读取 hart ID、传递设备树地址、找到固件入口
PC = 0x80000000，进入 OpenSBI
  ↓ 完成所需机器级启动和特权级交接
PC = 0x80200000，进入 kern_entry
  ↓ 内核不能依赖固件留下的栈，先设置 sp
sp = 0x80203000
  ↓ 尾跳转进入 C
PC = 0x8020000a，进入 kern_init
```

### 3. 输出链：从内核字符串到主机终端

```text
kern_init 想输出字符串
  ↓ 不能依赖尚不存在的 Linux 用户态 libc/syscall
cprintf 做格式化
  ↓ 逐字符交给 console abstraction
cons_putc
  ↓ 发起旧版 SBI console_putchar 服务
寄存器约定 + ecall
  ↓ OpenSBI 处理请求
QEMU 模拟的控制台输出
  ↓ -nographic 映射至终端
WSL 终端出现 (THU.CST) os is loading ...
```

### 4. 验证链：为什么不只看一个结果

```text
看源码        → 猜测会发生什么
看 ELF / 符号 → 证明编译产物的架构、入口与布局
看 QEMU 输出  → 证明整个启动可运行
用 GDB 单步   → 证明 PC 和 SP 的具体动态过程
```

四层证据互补，不能互相替代。

## 十二、读完以后应该能回答的题（附简短核对要点）

1. **为什么 QEMU 加载内核到 `0x80200000`，CPU 初始却在 `0x1000`？** 因为内存放置与初始 PC 是不同机制；Reset Vector 决定起始取指位置。
2. **为什么 `auipc t0,0x0` 执行后 `t0=0x1000`？** 计算当前指令 PC 加上立即数左移 12 位，此处偏移为零。
3. **`addi a1,t0,32` 与 `ld t0,24(t0)` 的差异？** 前者做寄存器加法得到地址，后者在计算出的地址上真正读取内存。
4. **为什么必须有 OpenSBI？** 不是所有 RISC-V 机器普遍必须使用此实现；当前设计用它负责机器级启动/服务并提供 SBI 接口。
5. **SBI 和 OpenSBI 是不是一样？** 不是；前者规定调用协议，后者是实现。
6. **为什么 `ecall` 可以服务请求？** 它触发同步 trap，CPU 转入配置的处理路径，由服务方按约定处理。
7. **为什么不直接从 OpenSBI 跳进任意 C 函数？** 内核需要保证自身栈及 ABI 前提；当前 `kern_entry` 负责建立栈。
8. **`bootstacktop` 存的是某个值吗？** 在这里它首先是汇编/链接符号，其地址代表预留栈的高地址边界。
9. **为什么执行一次 `si` 后 `sp` 恰好已正确？** 本次 `auipc` 的 PC 相对位移恰好得到 `0x80203000`，并非所有 `la` 都如此。
10. **为什么 `kern_init` 地址是 `0x8020000a` 而不是 `0x8020000c`？** 压缩指令可为 2 字节，不能假设每条指令恒为 4 字节。
11. **为什么打印需要 SBI？** 当前内核没有普通 Linux 用户态 libc，console 驱动选择由固件提供的 SBI 输出服务。
12. **为什么 GDB 读 ELF 但 CPU 执行 raw image？** ELF 提供调试符号，raw image 是实际装入虚拟内存的字节。
